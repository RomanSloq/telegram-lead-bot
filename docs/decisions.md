# Решения P4 v1

1. **Одна пользовательская работа:** оформить заявку на выездную услугу и
   обработать её в Telegram Mini CRM. Демо не выдается за бренд или круглосуточный
   сервис.
2. **Входящие updates:** штатный polling aiogram с `handle_as_tasks=False`.
   Сквозная гарантия относится к уже подтверждённой заявке, а не к каждому
   входящему update. Собственные poller и `processed_updates` не нужны.
3. **Сохранность:** `drafts`, `leads`, `deliveries` в SQLite. Подтверждение
   атомарно сохраняет заявку и все доставки. `leads.source_draft_id` уникален.
   Менеджерское уведомление может не отправиться, но заявка остаётся в `/leads`.
4. **Отправка:** один worker на один процесс. Handler только сигнализирует о
   новой работе; worker возобновляет due-доставки после рестарта. Возможный
   дубликат Telegram-сообщения после аварии содержит тот же ID заявки.
5. **Время и повторы:** часы внедряются в worker. Пять попыток всего, интервалы
   1, 5, 15, 60 минут; `retry_after` может продлить интервал. Истечение попыток
   и постоянная ошибка дают `failed`; ручной повтор создаёт новый лимит попыток.
6. **Доступ:** менеджерские команды, callbacks и запись заметки проверяют
   Telegram user ID и личный чат на сервере. Список ID задаётся локально.
7. **Данные:** черновик клиента переживает рестарт. Незавершённый ввод заметки
   менеджера временный; сохранённая заметка постоянна. Каталог, название демо и основные подсказки находятся в
   `catalog.py`; остальные сообщения интерфейса остаются в handlers.
8. **Scope:** без web UI, внешней CRM, AI, платежей, брокера, ORM и multi-tenant.
   Постоянное размещение и правила хранения персональных данных — отдельные
   решения перед реальным использованием.
